# 01. Верхнеуровневая архитектура PACK.IT

## 1. Назначение системы

PACK.IT — приложение для управления техническими проектами мероприятий: от первичной сметы до комплектации, склада, документов и закрытия проекта.

Система должна поддерживать разные сценарии:

- простая смета без 3D;
- проект с техническими разделами;
- проект со складской проверкой;
- проект с 3D-сценой;
- проект с командой и транспортом;
- проект с документами для клиента и внутренней команды;
- проект с резервами, дефицитом и субарендой.

## 2. Центральная архитектурная формула

```text
Project / Quote
→ Sections
→ Optional 3D Scene
→ BOM
→ Inventory Availability / Reservations
→ Shortages / Subrent
→ Warehouse Operations
→ Documents
→ Status / History / CRM
```

## 3. Основные модули и продуктовые контексты

### 3.1. Project / Quote Core

Главный модуль приложения.

Отвечает за:

- создание проекта;
- клиента;
- площадку;
- даты;
- статусы;
- разделы сметы;
- коммерческие суммы;
- внутреннюю техническую комплектацию;
- проектную историю изменений;
- ссылки на документы, складские read models и 3D-сцену.

`Project / Quote Core` формирует потребность проекта, но не владеет складскими остатками, резервами, дефицитами, субарендой или складскими движениями.

### 3.2. Sections Engine

Модуль технических разделов проекта.

Разделы могут включать:

- сцену;
- фермы;
- LED;
- звук;
- свет;
- коммутацию;
- backline;
- услуги;
- команду;
- транспорт;
- прочие позиции.

Разделы должны работать как без 3D, так и с 3D.

### 3.3. Optional 3D Scene Module

Подключаемый модуль, который открывается из проекта только при необходимости.

Отвечает за:

- 3D-сцену проекта;
- визуальное построение сцены, ферм, LED и оборудования;
- SceneModel;
- связь 3D-объектов с BOM;
- схемы для документов;
- визуализацию для клиента и технической команды.

3D-модуль не должен блокировать создание обычной сметы.

### 3.4. BOM Engine

Модуль формирования комплектации.

Отвечает за:

- нормализацию строк комплектации;
- объединение строк из разных разделов;
- расчёт количества;
- вес;
- мощность;
- стоимость;
- источник строки;
- связь со складской номенклатурой.

BOM может формироваться из ручных разделов или из 3D-сцены.

BOM описывает **потребность**, но не является источником истины для остатков, резервов, дефицитов и субаренды. Эти состояния возвращаются в проект через ссылки и read-model проекции соответствующих контекстов.

### 3.5. Складской контур

В интерфейсе складской контур может выглядеть как единый раздел «Склад», но в backend он разделён на самостоятельные продуктовые контексты.

#### 3.5.1. Catalog

Отвечает за описание номенклатуры, категории, коды, единицы измерения и технические характеристики.

#### 3.5.2. Inventory

Отвечает за:

- складские единицы и количественные остатки;
- склады и локации;
- состояние оборудования;
- учётные корректировки;
- расчёт текущей доступности.

`inventory` не владеет резервами, жизненным циклом дефицита, субарендой, выдачей или возвратом.

#### 3.5.3. Reservations

Отвечает за:

- запросы на резерв;
- подтверждение резерва;
- освобождение резерва;
- конфликты резервов;
- сроки действия;
- связь резерва с проектом и BOM.

#### 3.5.4. Shortages

Отвечает за:

- создание подтверждённой нехватки;
- открытое количество;
- назначение ответственного;
- предложения результата;
- принятие предложения;
- принятие с корректировкой;
- отдельные финальные решения;
- частичное и полное закрытие;
- доменную историю нехватки.

#### 3.5.5. Subrent

Отвечает за закрытие потребности внешним источником:

- поставщика;
- количество;
- стоимость;
- подтверждение и отмену;
- связь с проектом и нехваткой.

#### 3.5.6. Warehouse Operations

Отвечает за физические и учётно значимые складские движения:

- выдачу;
- возврат;
- перемещение;
- списание;
- складские документы и движения.

Канонические границы складского контура описаны в `05_INVENTORY_RESERVATIONS.md`.

### 3.6. Documents Module

Модуль документов и PDF.

Отвечает за:

- коммерческое предложение;
- техническую сводку;
- складской лист;
- монтажный лист;
- внутренний расчёт;
- схемы;
- экспорт PDF;
- шаблоны документов;
- фирменный стиль.

Документы формируются из подтверждённых данных владельцев соответствующих контекстов, а не из случайного состояния UI.

### 3.7. Notifications

Отвечает за доставку уведомлений по уже принятым решениям других контекстов.

`notifications` не принимает бизнес-решения, не закрывает дефицит, не создаёт резерв и не меняет складской остаток.

### 3.8. Audit

Отвечает за системный журнал значимых действий.

Audit log не заменяет:

- проектную историю;
- историю резерва;
- доменную историю нехватки;
- историю складской операции.

### 3.9. Admin Console

Системная админка приложения.

Отвечает за:

- пользователей;
- роли;
- права;
- ключи доступа;
- приглашения;
- настройки компании;
- логотипы;
- шаблоны PDF;
- справочники;
- системные настройки;
- аудит;
- управление модулями.

Системная роль администратора не предоставляет складские или проектные permissions автоматически.

### 3.10. Auth / Access Control

Модуль авторизации и прав доступа.

Должен поддерживать:

- вход пользователя;
- роли;
- permissions по контекстам и действиям;
- scope доступа;
- ограниченный доступ приглашённых специалистов;
- временные и постоянные ключи;
- журнал действий;
- будущую многофакторную авторизацию.

### 3.11. Sync / Offline Module

Модуль локальной работы и синхронизации.

Должен поддерживать:

- локальные черновики;
- автосохранение;
- работу при плохом интернете;
- очередь явно поддерживаемых отложенных действий;
- безопасную синхронизацию;
- защиту от потери проекта.

Складские движения, резервы, права и финальное закрытие нехватки не подтверждаются окончательно только локальным клиентом.

## 4. Принцип модульности

PACK.IT строится как модульный монолит с progressive DDD-lite: одна backend-кодовая база и одна основная PostgreSQL на старте, но с явными продуктовыми контекстами, владельцами данных и направлением зависимостей.

Каждый модуль должен иметь понятный контракт и единственную публичную границу.

Другой контекст вызывается только через его публичный `index.ts` или явно определённый application port. Прямой импорт чужого repository/ORM adapter запрещён.

Запрещено строить приложение так, чтобы UI напрямую управлял складом, документами, резервами и расчётами без application/domain слоя.

Правильная схема:

```text
UI
→ API Contract
→ Transport
→ Application Use Case
→ Domain Logic / Ports
→ Infrastructure Adapter
→ PostgreSQL / External Provider
```

Для межмодульного складского сценария:

```text
Shortages use case
→ Inventory / Warehouse Operations / Subrent public port
→ transaction or outbox-compatible boundary
→ domain event
→ Notifications / Audit
```

Неправильная схема:

```text
Button click
→ direct mutation everywhere
→ shortage / inventory / notification / PDF side effects
```

Архитектурные границы должны проверяться автоматически командой `architecture:check`, а не существовать только в документации.

## 5. Главное ограничение

3D-сцена не должна быть единственным источником проекта.

Проект может быть создан и завершён без 3D-сцены.
