# 09. Backend и архитектура данных PACK.IT

## 1. Статус решения

Этот документ фиксирует техническую архитектурную базу PACK.IT CRM Next до начала активной разработки.

Базовый подход:

```text
модульный монолит
+ progressive DDD-lite
+ общие API-контракты
+ автоматическая проверка архитектурных границ
+ PostgreSQL как источник истины
```

Это не окончательный выбор конкретного runtime, web-framework или облачного провайдера. Bun, Node.js, Hono, Fastify, NestJS и варианты размещения должны сравниваться отдельно. Архитектурные границы, описанные здесь, не зависят от выбранного framework.

## 2. Почему не микросервисы

На старте PACK.IT должен разрабатываться как один продукт, одна кодовая база backend и одна основная база данных.

Микросервисы до появления подтверждённой эксплуатационной необходимости запрещены, потому что они преждевременно добавляют:

- сетевые сбои между частями одной бизнес-операции;
- распределённые транзакции;
- отдельные схемы деплоя;
- сложную трассировку;
- дублирование контрактов и инфраструктуры;
- повышенную стоимость эксплуатации.

При этом модульный монолит не означает смешивание всех функций. Каждый продуктовый контекст получает собственную границу, публичный API и правила зависимостей.

## 3. Progressive DDD-lite

Доменная архитектура применяется по необходимости, а не ради одинакового дерева папок.

Для простого справочника могут быть достаточны:

```text
transport
application
infrastructure
```

Для модуля с расчётами, ограничениями и переходами состояния добавляется:

```text
domain
```

Запрещено создавать без реальной необходимости:

- пустые архитектурные слои;
- универсальные `BaseRepository` и generic CRUD-репозитории;
- CQRS;
- event sourcing;
- отдельные сервисы и брокеры;
- абстракции, которые не решают существующую проблему.

## 4. Предлагаемая форма monorepo

```text
apps/
  api/                 # HTTP API и composition root
  web/                 # внутренняя CRM после авторизации
  website/             # публичный сайт, документация и SEO-страницы
  worker/              # фоновые задачи, когда они появятся
  cron/                # именованные периодические задачи

packages/
  contracts/           # Zod-схемы, DTO и стабильные ошибки API
  domain-shared/       # только действительно общие value objects и политики
  ui/                  # базовые UI-примитивы и дизайн-система
  config/              # общие конфигурации TypeScript/lint/test

backend/
  modules/             # продуктовые контексты модульного монолита

scripts/
  architecture-check.* # проверка допустимых импортов
  repository-checks.*  # проверки окружения и репозитория

docs/
  ...
```

Физическое расположение `backend/modules` может позднее стать `apps/api/src/modules`. Важна не конкретная папка, а владение контекстом и направление зависимостей.

## 5. Продуктовые контексты PACK.IT

Начальный список контекстов:

```text
identity-access
organizations
users
clients
projects-quotes
sections
catalog
bom
inventory
reservations
shortages
subrent
warehouse-operations
team
transport
files
three-d-scene
documents
notifications
chat
audit
settings
```

Это карта ответственности, а не требование немедленно создать все модули.

### 5.1. Ключевые границы

- `projects-quotes` владеет проектом, сметой, статусами и общей оркестрацией проекта.
- `sections` владеет техническими разделами сметы, но не складскими остатками.
- `bom` нормализует потребность проекта и происхождение строк комплектации.
- `inventory` владеет номенклатурой, складскими единицами и остатками.
- `reservations` владеет резервированием потребности под проект.
- `shortages` владеет жизненным циклом подтверждённого дефицита.
- `subrent` владеет закрытием дефицита внешним источником.
- `warehouse-operations` владеет выдачей, возвратом, перемещением и списанием.
- `three-d-scene` владеет сценой и объектами, но отдаёт результат через BOM/sections.
- `documents` формирует документы из подтверждённых данных других контекстов.
- `notifications` доставляет уведомления, но не принимает бизнес-решения за исходный модуль.
- `audit` хранит значимые действия и изменения, но не подменяет доменную историю.

## 6. Внутренняя структура backend-модуля

```text
modules/<context>/
  index.ts             # единственная публичная граница модуля
  transport/           # HTTP, валидация входа, представление ответа
  application/         # use cases, права, транзакции, оркестрация
  domain/              # опциональные чистые правила, расчёты и переходы
  infrastructure/      # PostgreSQL/ORM и внешние provider-адаптеры
```

Рекомендуемое направление:

```text
transport -> application -> domain/ports <- infrastructure
```

DTO находятся на внешней границе и не должны становиться внутренней доменной моделью по умолчанию.

## 7. Обязательные правила зависимостей

### 7.1. Transport

Transport может:

- разобрать HTTP-запрос;
- проверить контракт;
- получить authenticated principal;
- вызвать application use case;
- преобразовать результат или ошибку в стабильный HTTP-ответ.

Transport не может:

- напрямую обращаться к ORM;
- выполнять складские или финансовые расчёты;
- управлять транзакциями продукта;
- вызывать SDK хранилища, почты или облака напрямую.

### 7.2. Application

Application отвечает за:

- бизнес-сценарий;
- авторизацию действия;
- транзакционную границу;
- координацию доменных правил;
- вызов портов своего или явно подключённого контекста.

Application не импортирует HTTP-framework, ORM, environment-конфигурацию или provider SDK.

### 7.3. Domain

Domain содержит только чистые правила:

- расчёты;
- политики;
- переходы состояния;
- value objects;
- инварианты.

Domain не знает о React, HTTP, ORM, файловом хранилище, очереди или облачном провайдере.

### 7.4. Infrastructure

Infrastructure реализует контекстные порты:

- чтение и запись PostgreSQL;
- объектное хранилище;
- почта;
- push;
- внешние интеграции.

Репозитории должны выражать операции продукта, а не универсальный CRUD.

Хорошо:

```text
reserveAvailableItemsForProject(...)
findConflictingReservations(...)
closeShortageWithSubrent(...)
```

Плохо:

```text
BaseRepository<T>.create/update/delete
```

### 7.5. Межмодульное взаимодействие

Другой модуль импортируется только через его публичный `index.ts` или через явно определённый application port.

Запрещено:

```text
projects-quotes -> inventory/infrastructure/prisma-repository
```

Допустимо:

```text
projects-quotes -> inventory/index.ts
```

или узкий порт:

```text
InventoryAvailabilityPort
```

## 8. Shared contracts

`packages/contracts` является источником истины для внешних форм обмена:

- request schemas;
- response schemas;
- DTO;
- pagination;
- стабильные API errors;
- версии публичных событий realtime, если они вводятся.

Контракты создаются через Zod или эквивалентную schema-first библиотеку.

Backend использует их для проверки входа и выхода. Web и будущий mobile используют те же схемы в API-клиентах и формах.

Запрещено:

- вручную копировать интерфейсы API в каждом клиенте;
- импортировать Prisma-модели в contracts;
- помещать в contracts внутреннее состояние UI;
- превращать contracts в общую папку всех типов проекта;
- связывать contracts с React, ORM или provider SDK.

Изменение контракта проверяется одновременно у producer и всех consumers.

## 9. Web и публичный website

PACK.IT должен разделять две браузерные поверхности.

### 9.1. Внутренняя CRM (`apps/web`)

Предназначена для:

- проектов и смет;
- склада;
- комплектации;
- команды и транспорта;
- админки;
- внутренних документов;
- 3D-конструктора;
- экранов после входа.

Эти страницы не требуют SEO. Архитектура может быть CSR или иным подходом, выбранным позднее.

### 9.2. Публичный сайт (`apps/website`)

Предназначен для:

- лендинга;
- публичной документации;
- страниц продукта;
- публичного каталога или marketplace, если он появится;
- SEO и rich link previews.

Публичный сайт не должен дублировать внутреннюю CRM.

## 10. Правила frontend

Предлагаемая структура:

```text
src/
  features/<context>/
    index.ts
    api/
    model/
    ui/
  platform/
  components/ui/
  routes/
```

Правила:

- feature экспортирует публичную поверхность через `index.ts`;
- один feature не импортирует внутренние файлы другого feature;
- `platform` и UI-примитивы не импортируют продуктовые features;
- routes/pages являются композиционными файлами;
- серверное состояние отделяется от локального UI-состояния;
- бизнес-правила не дублируются в компонентах;
- закрытые продуктовые компоненты получают семантические данные и callbacks, а не универсальный доступ к API.

## 11. PostgreSQL и данные

PostgreSQL является основным источником истины для:

- проектов и смет;
- складских остатков и операций;
- резервов;
- дефицитов и субаренды;
- сообщений и уведомлений;
- аудита;
- прав и сессий;
- метаданных файлов и документов.

Конкретная минимальная версия PostgreSQL и стратегия идентификаторов принимаются отдельным ADR.

UUIDv7 можно рассмотреть, но нельзя делать PostgreSQL 18 обязательным только потому, что это использовано в стороннем шаблоне.

### 11.1. Транзакции

Транзакционная граница определяется application use case.

Операции, которые меняют взаимосвязанные состояния, должны быть атомарными. Примеры:

- подтверждение резерва и пересчёт доступности;
- закрытие дефицита и фиксация источника результата;
- выдача оборудования и создание складских движений;
- изменение роли и отзыв активных сессий;
- подтверждение финального результата проекта и фиксация истории.

### 11.2. Controlled writes

Критические таблицы нельзя изменять произвольным клиентским CRUD.

Записи выполняются через именованные use cases, которые проверяют:

- права;
- текущий статус;
- допустимость перехода;
- конфликтующие операции;
- идемпотентность;
- аудит.

### 11.3. RLS

RLS может использоваться как дополнительный уровень защиты, но не заменяет application authorization и доменные проверки.

До выбора схемы multi-tenancy решение по RLS остаётся открытым.

## 12. Auth и доступ

PACK.IT не должен автоматически копировать простую модель `user | admin` или чужую custom JWT-реализацию.

Требования PACK.IT включают:

- компании/организации;
- системные и организационные роли;
- права по модулям и действиям;
- приглашённых специалистов;
- временный доступ;
- отзыв доступа;
- журнал действий;
- будущую MFA;
- изоляцию данных компаний.

Конкретная auth-система принимается отдельным документом и threat model.

Токены, cookies, session rotation, social auth и password reset должны проходить отдельный security review.

## 13. Файлы и документы

Постоянные пользовательские файлы не хранятся на эфемерной файловой системе контейнера.

Backend владеет доступом к объектному хранилищу через отдельный порт.

Нужно различать:

- исходные загрузки;
- оптимизированные варианты;
- временные файлы;
- сгенерированные документы;
- публичные и приватные объекты;
- сроки хранения и удаление.

Метаданные и права доступа хранятся в PostgreSQL. Сам объект хранится в S3-совместимом хранилище или эквиваленте.

## 14. Worker, cron и асинхронные задачи

Backend может иметь отдельные entrypoints из одной кодовой базы:

```text
api
worker
cron
```

Они не должны превращаться в отдельные микросервисы без причины.

Worker включается только после появления конкретных задач, например:

- генерация тяжёлых PDF;
- обработка изображений и 3D-ресурсов;
- массовый импорт;
- отправка уведомлений;
- интеграционные синхронизации.

Cron создаётся только для именованных периодических задач:

- напоминания;
- проверка просроченных резервов;
- очистка временных данных;
- регламентные сверки.

Каждая фоновая задача должна иметь:

- идемпотентность;
- retry policy;
- ограничение количества попыток;
- timeout;
- журнал результата;
- понятный способ повторного запуска.

## 15. Realtime

Чаты, presence, live notifications и совместное редактирование сначала могут работать через тот же backend.

При одном экземпляре backend допустим локальный registry WebSocket/SSE-соединений.

При горизонтальном масштабировании добавляется Redis-совместимый Pub/Sub, например Valkey, для fanout между экземплярами.

При этом:

```text
PostgreSQL = источник истины
Pub/Sub = доставка события
WebSocket/SSE = доставка клиенту
```

Сообщения, уведомления и audit-relevant события не должны существовать только в Pub/Sub.

Клиент после переподключения восстанавливает состояние чтением API, а не рассчитывает получить всю историю из realtime-канала.

## 16. Доменные события

Внутренние доменные события допустимы как способ ослабить связи между модулями, но не должны сразу требовать Kafka или внешнего брокера.

Примеры:

```text
ProjectApproved
ReservationConfirmed
ShortageCreated
ShortageResolved
WarehouseIssueCompleted
DocumentGenerated
UserAccessRevoked
```

На первом этапе события могут доставляться внутри процесса после успешной транзакции через outbox-compatible границу.

Для важных межпроцессных эффектов должна быть предусмотрена transactional outbox, чтобы событие не потерялось между commit и публикацией.

## 17. Offline и синхронизация

Offline-first не должен означать произвольное слияние всех данных на клиенте.

Разрешённый первый этап:

- локальные черновики;
- автосохранение;
- очередь явно поддерживаемых действий;
- optimistic UI только для безопасных операций;
- версия/etag для обнаружения конфликта;
- сервер как финальный арбитр прав и переходов.

Складские движения, резервы, выдача, возврат, права и финансово значимые изменения не подтверждаются окончательно только локальным клиентом.

Полная offline-синхронизация проектируется отдельным документом после определения конкретных мобильных сценариев.

## 18. Архитектурная проверка как обязательный gate

Архитектурные правила должны исполняться автоматически.

В репозитории требуется собственная команда, например:

```text
architecture:check
```

Она должна проверять минимум:

1. `domain` и `application` не импортируют framework, ORM, env и provider SDK.
2. `transport` не импортирует ORM и внешние provider SDK.
3. Чужой backend-модуль импортируется только через публичный `index.ts`.
4. Frontend feature импортируется извне только через публичный `index.ts`.
5. `platform` и базовые UI-компоненты не импортируют features.
6. `packages/contracts` не импортирует приложения, ORM, UI-framework или provider SDK.
7. Запрещённые циклические зависимости завершают проверку ошибкой.

Нарушение должно выводиться как:

```text
path:line [rule] description
```

Проверка должна иметь fixture-тесты для каждой группы правил.

После появления кода команда запускается:

- локально;
- перед commit по желанию команды;
- обязательно в CI каждого pull request;
- перед release build.

## 19. Базовая validation ladder

После появления кода минимальная лестница проверки:

```text
install --frozen
architecture:check
typecheck
contracts tests
backend unit tests
backend integration tests
web tests
web e2e smoke
build
```

Наличие общей команды `test` не отменяет отдельных адресных команд для быстрой разработки.

## 20. Deployment и облако

Техническая архитектура не должна жёстко привязывать продукт к DigitalOcean, Yandex Cloud или конкретному VPS.

Минимальные абстракции:

- PostgreSQL;
- S3-compatible object storage;
- container runtime;
- reverse proxy/load balancer;
- secret delivery;
- optional Redis-compatible Pub/Sub;
- observability.

Выбор провайдера должен учитывать:

- требования к персональным данным и локализации;
- ФЗ и требования РКН;
- доступность оплаты;
- стоимость;
- резервирование;
- backups и disaster recovery;
- доступность managed PostgreSQL/object storage;
- эксплуатационные возможности команды.

Конкретная production topology фиксируется отдельным ADR и runbook.

## 21. Наблюдаемость и аудит

Необходимо различать:

- технические логи;
- metrics;
- traces;
- продуктовый audit log;
- доменную историю сущности.

В технические логи не должны попадать пароли, токены, секреты, полные персональные данные и содержимое приватных сообщений.

Каждый request должен иметь correlation/request ID. Фоновые задачи должны сохранять job ID и причинную связь с исходным действием.

Audit log должен фиксировать значимые действия, но не быть единственным источником текущего состояния.

## 22. Безопасность

До production обязательны:

- threat model;
- модель multi-tenancy;
- матрица ролей и разрешений;
- CSRF/XSS/SSRF/upload protections;
- rate limiting;
- secret management;
- backup/restore validation;
- dependency and container scanning;
- журналирование административных действий;
- политика хранения и удаления данных;
- отдельная проверка чатов и E2EE-границ.

## 23. Решения, которые пока не приняты

Открытыми остаются:

- Node.js или Bun;
- Hono, Fastify, NestJS или другой backend framework;
- конкретный ORM/query builder;
- PostgreSQL minimum version;
- стратегия ID;
- auth/session provider;
- точная модель multi-tenancy;
- RLS;
- frontend framework и rendering strategy;
- очередь фоновых задач;
- production provider;
- мобильное приложение и его release pipeline.

Ни одно из этих открытых решений не отменяет модульный монолит, контракты и проверяемые границы.

## 24. Порядок внедрения

### Этап A — до кода

1. Утвердить карту контекстов.
2. Уточнить владельцев данных и межмодульные контракты.
3. Утвердить модель организаций, пользователей и прав.
4. Принять ADR по стеку, базе, auth и deployment.

### Этап B — bootstrap репозитория

1. Создать monorepo.
2. Создать минимальные `apps` и `packages`.
3. Реализовать `architecture:check` до появления большого количества кода.
4. Добавить contracts package и общий error shape.
5. Настроить CI PR-gates.

### Этап C — первый вертикальный срез

Первый срез должен пройти целиком:

```text
contract
-> route
-> application use case
-> domain rule при необходимости
-> repository adapter
-> PostgreSQL
-> web feature
-> integration/e2e test
```

Рекомендуемый первый срез:

```text
organization
-> user session
-> client
-> project/quote draft
```

Склад, realtime, worker и 3D не должны подключаться раньше, чем базовый срез подтверждён тестами.

## 25. Принятое направление

PACK.IT CRM Next строится как долгоживущий модульный продукт, а не как набор экранов вокруг общей базы.

Главные технические правила:

```text
один backend на старте
одна основная PostgreSQL
чёткие продуктовые контексты
contracts как внешняя истина
бизнес-логика вне UI и HTTP handlers
доступ к чужому модулю только через публичную границу
автоматическая architecture check
worker/realtime/broker только по реальной необходимости
```
