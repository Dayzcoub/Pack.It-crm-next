# 10.451. Упрощённая модель доступности оборудования для техпродакшна

## Решение

В MVP PACK.IT складской контур не должен превращаться в полноценную WMS. Для ежедневного планирования мероприятий используются понятные пользователю операционные количества и состояния оборудования.

Для каждой номенклатурной позиции система должна уметь показать как минимум:

- **Всего** — общее количество оборудования, принадлежащего компании;
- **Зарезервировано** — количество, занятое подтверждёнными проектными резервами на рассматриваемые даты;
- **На выезде** — количество, фактически выданное на мероприятия и ещё не возвращённое;
- **В долгосрочной аренде** — количество собственного оборудования, временно выведенного из обычного событийного оборота на длительный срок, с указанием, где оно находится;
- **Неисправно** — количество в состоянии `Blocked`;
- **Не вернулось** — количество с открытым складским расхождением `missing/outstanding`;
- **Доступно** — количество, которое реально можно назначить новому проекту на выбранные даты.

## Ключевые правила

- `issue` и `return` не изменяют показатель **Всего**: оборудование остаётся собственностью компании;
- покупка или другое добавление оборудования увеличивает **Всего** через явную `stock_addition` операцию;
- списание уменьшает **Всего** через отдельную операцию `writeoff`;
- `Blocked`, `missing/outstanding`, нахождение на выезде и долгосрочная аренда уменьшают фактическую доступность, но сами по себе не означают списание;
- проектные резервы по-прежнему ведутся по номенклатурной позиции и количеству и не связываются с серийными номерами;
- серийные номера остаются отдельными данными `inventory` и используются только там, где это действительно нужно: например, для конкретной неисправности, недостачи или другого точечного исключения;
- долгосрочная аренда должна хранить пользовательское описание места/контрагента, чтобы было понятно, где находится оборудование.

## Product principle

Главная задача складского контура PACK.IT — отвечать на вопрос планирования:

> сколько оборудования реально можно использовать для нового проекта на нужные даты?

Сложные WMS-понятия и дополнительные технические buckets не должны появляться в пользовательской модели, пока они не нужны реальному процессу техпродакшна.

Это решение развивает 10.450 и заменяет необходимость вводить отдельные пользовательские показатели `owned_total` и `warehouse_present` из формулировки вопроса 10.451: для MVP используется один понятный показатель **Всего** плюс отдельные состояния/занятость, влияющие на **Доступно**.
