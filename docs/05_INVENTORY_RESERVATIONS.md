# 05. Склад, резервы, дефициты и складские операции

## 1. Статус решения

Этот документ является канонической доменной привязкой складского контура PACK.IT CRM Next.

Складской контур не является одним большим модулем. Он разделён на продуктовые контексты с собственными владельцами данных и публичными application-границами:

```text
catalog
inventory
reservations
shortages
subrent
warehouse-operations
notifications
audit
```

Слово «склад» допустимо в интерфейсе как пользовательский раздел, но не как единый владелец всех складских данных и действий.

## 2. Владельцы данных

### 2.1. `catalog`

Владеет описанием номенклатуры:

- названием и кодом позиции;
- типом и категорией;
- единицей измерения;
- техническими характеристиками;
- связями с комплектами и справочниками.

### 2.2. `inventory`

Владеет фактическим учётом:

- складскими единицами;
- количественными остатками;
- складами и локациями;
- состоянием оборудования;
- учётными корректировками;
- текущей доступностью как производной от остатков и подтверждённых резервов.

`inventory` не владеет жизненным циклом проекта, резерва, дефицита или субаренды.

### 2.3. `reservations`

Владеет резервированием потребности проекта:

- запросом на резерв;
- подтверждением или освобождением резерва;
- конфликтами резервов;
- сроком действия резерва;
- связью резерва с проектом и строкой BOM.

### 2.4. `shortages`

Владеет жизненным циклом подтверждённой нехватки:

- созданием нехватки;
- открытым количеством;
- назначением ответственного;
- предложением результата;
- принятием предложения;
- принятием с корректировкой;
- отдельным финальным действием;
- частичным и полным закрытием;
- доменной историей нехватки.

Все решения серии `25_WAREHOUSE_10_xxx.md`, относящиеся к предложениям ответственного и их подтверждению, принадлежат контексту `shortages`.

### 2.5. `subrent`

Владеет закрытием потребности внешним источником:

- заявкой на субаренду;
- поставщиком;
- количеством;
- стоимостью;
- подтверждением и отменой;
- связью с конкретной нехваткой и проектом.

### 2.6. `warehouse-operations`

Владеет физическими и учётно значимыми складскими движениями:

- выдачей;
- возвратом;
- перемещением;
- списанием;
- соответствующими складскими документами и движениями.

### 2.7. `notifications`

Доставляет уведомления, но не принимает решение за `shortages` и не изменяет состояние нехватки.

### 2.8. `audit`

Фиксирует значимые действия для системного контроля, но не заменяет доменную историю нехватки, резерва или складской операции.

## 3. Связь с проектом и BOM

`projects-quotes` и `bom` формируют потребность проекта, но не владеют складскими остатками, резервами, дефицитами и субарендой.

Правильная схема:

```text
Project / Quote
→ Sections
→ BOM demand
→ Reservations
→ Inventory availability
→ Shortage when demand is not covered
→ Subrent or another resolution
→ Warehouse operations
```

В проекте допускается хранить только ссылки и read-model проекции:

- идентификаторы резервов и нехваток;
- сводный статус обеспечения;
- рассчитанные количества `available / reserved / shortage / subrent`;
- время последнего пересчёта.

Эти значения не являются источником истины и не изменяются прямым CRUD из `projects-quotes`.

## 4. Жизненный цикл нехватки

```text
open
→ assigned
→ proposal_submitted
→ proposal_accepted | proposal_accepted_with_adjustment | resolved_by_separate_action
→ partially_resolved | resolved
```

Названия технических статусов могут быть уточнены позднее, но переходы выполняются только именованными application use cases контекста `shortages`.

Примеры use cases:

```text
assignShortageResponsible(...)
submitShortageResolutionProposal(...)
acceptShortageProposal(...)
acceptShortageProposalWithAdjustment(...)
resolveShortageWithSeparateResult(...)
```

## 5. Предложение ответственного

Назначенный ответственный:

- исследует нехватку;
- предлагает результат;
- указывает обязательные для типа результата данные;
- не закрывает нехватку самостоятельно, если у него нет отдельного permission на финальное разрешение.

Поддерживаемые типы предложения:

```text
found
write_off
accounting_error
other
```

Требования:

- `found` — обязательно найденное количество;
- `write_off` — обязательна причина списания;
- `accounting_error` — обязательно пояснение ошибки учёта;
- `other` — обязателен комментарий.

## 6. Подтверждение и отдельное финальное действие

Финальное действие может выполнить только пользователь с соответствующим permission. Название должности или системная роль сами по себе не дают это право.

Базовые permissions:

```text
shortages.assign
shortages.propose_resolution
shortages.accept_proposal
shortages.resolve
```

Обычное принятие сохраняет предложенный тип и данные.

Принятие с корректировкой:

- сохраняет тот же тип результата;
- может уменьшать предложенное количество, но не увеличивать его;
- требует причину корректировки;
- связано с исходным предложением;
- оставляет незакрытый остаток открытым.

Изменение типа результата или увеличение предложенного количества является отдельным финальным действием, а не принятием предложения.

## 7. Межмодульные последствия результата

Контекст `shortages` принимает финальное решение и координирует последствия через публичные границы других контекстов.

### 7.1. `found`

`shortages` уменьшает открытое количество на подтверждённое найденное количество.

Если для найденного оборудования требуется изменение учётного остатка или локации, это выполняется отдельным именованным use case через `inventory` или `warehouse-operations`.

### 7.2. `write_off`

`shortages` не изменяет остатки напрямую.

Финальное разрешение должно вызвать публичный use case `warehouse-operations` для создания списания и только после его успешного выполнения зафиксировать соответствующее закрытие нехватки.

### 7.3. `accounting_error`

Учётная корректировка выполняется публичным use case контекста `inventory`. После успешной корректировки `shortages` фиксирует частичное или полное разрешение нехватки.

### 7.4. `other`

Результат фиксируется в `shortages`. Если он требует изменения другого контекста, это должно быть явно выражено отдельным application port/use case, а не прямой записью в чужую таблицу.

### 7.5. Субаренда

Субаренда оформляется через `subrent` и связывается с нехваткой. `shortages` получает подтверждённый результат через публичную границу или доменное событие.

## 8. Транзакции и события

Application use case определяет транзакционную границу.

Критическое состояние нехватки не должно закрываться до успешного выполнения обязательного межмодульного действия.

После успешной транзакции `shortages` может публиковать доменные события:

```text
ShortageProposalSubmitted
ShortageProposalAccepted
ShortageProposalAcceptedWithAdjustment
ShortagePartiallyResolved
ShortageResolved
```

`notifications` подписывается на события и доставляет уведомления. Для важных асинхронных эффектов используется outbox-compatible граница.

## 9. История и аудит

Нужно различать:

- **доменную историю нехватки** — предложения, подтверждения, корректировки, результаты и остаток;
- **audit log** — кто, когда и из какого контекста выполнил значимое действие;
- **уведомление** — сообщение пользователю о уже принятом решении.

Источником текущего состояния является `shortages`, а не audit log и не notification record.

## 10. Permissions складского контура

Рекомендуемая начальная карта:

```text
catalog.view
catalog.edit

inventory.view
inventory.edit_items
inventory.correct_balance
inventory.view_costs

reservations.view
reservations.create
reservations.confirm
reservations.release

shortages.view
shortages.assign
shortages.propose_resolution
shortages.accept_proposal
shortages.resolve

subrent.view
subrent.create
subrent.confirm
subrent.cancel

warehouse_operations.view
warehouse_operations.issue
warehouse_operations.return
warehouse_operations.move
warehouse_operations.writeoff
```

Роли собираются из permissions. `System Admin`, `Director`, `Warehouse Manager` и любые другие названия не должны автоматически обходить application authorization.

## 11. Правила UI

UI может объединять контексты в один пользовательский раздел «Склад», но каждое действие вызывает конкретный API contract и application use case.

Запрещено:

```text
button
→ direct ORM/table mutation
→ simultaneous shortage/inventory/notification side effects
```

Правильно:

```text
UI
→ shortage contract
→ shortages application use case
→ public module ports
→ transaction/outbox
→ notification delivery
```

## 12. Связь с decision notes 10.294–10.313

Решения `10.294–10.313` сохраняют продуктовый смысл и трактуются так:

- владелец workflow — `shortages`;
- confirmer — пользователь с `shortages.accept_proposal` или `shortages.resolve`;
- история — доменная история нехватки;
- системный audit записывается отдельно;
- уведомления доставляет `notifications` после успешного решения;
- списание и учётная корректировка выполняются через публичные границы соответствующих контекстов.

При конфликте терминов эта архитектурная привязка имеет приоритет над ранними формулировками `warehouse keeper, admin, or director`.
