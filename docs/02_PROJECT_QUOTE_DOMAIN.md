# 02. Доменная модель Проекта / Сметы

## 1. Главная сущность

Главная рабочая сущность PACK.IT — **Проект / Смета**.

В интерфейсе пользователь может воспринимать её как смету, проект, заказ или мероприятие, но в архитектуре это один центральный объект.

Рабочее название доменной сущности:

```text
ProjectQuote
```

## 2. Задача ProjectQuote

ProjectQuote должен объединять:

- коммерческую часть;
- техническую часть;
- клиента;
- площадку;
- даты;
- команду;
- транспорт;
- потребность проекта;
- ссылки и read-model проекции складского обеспечения;
- документы;
- статусы;
- проектную историю;
- опциональную 3D-сцену.

ProjectQuote не является владельцем складских остатков, резервов, дефицитов, субаренды и складских движений.

## 3. Базовая структура ProjectQuote

```text
ProjectQuote
├── identity
├── client
├── venue
├── schedule
├── status
├── sections
├── optionalScene
├── bomDemand
├── fulfillmentProjection
├── crew
├── transport
├── documents
├── totals
├── permissions
└── history
```

`fulfillmentProjection` — это read model для интерфейса проекта. Источниками истины остаются `inventory`, `reservations`, `shortages`, `subrent` и `warehouse-operations`.

## 4. Identity

Идентификация проекта:

- id;
- номер проекта;
- название;
- рабочее описание;
- organization/workspace id;
- автор;
- ответственный менеджер;
- дата создания;
- дата обновления.

## 5. Client

Клиент:

- тип клиента: физическое лицо / компания;
- имя или название;
- контактное лицо;
- телефон;
- email;
- реквизиты;
- комментарий;
- история проектов клиента.

## 6. Venue

Площадка:

- название;
- адрес;
- контакт площадки;
- особенности заезда;
- лифт / пандус / этаж;
- электричество;
- ограничения по времени;
- комментарии;
- файлы и фото площадки в будущем.

## 7. Schedule

Даты:

- дата мероприятия;
- период мероприятия;
- дата монтажа;
- время монтажа;
- дата демонтажа;
- время демонтажа;
- смены;
- дедлайны подготовки;
- внутренние контрольные точки.

## 8. Status

Проект должен иметь управляемый статус.

Предварительный набор:

```text
draft
in_progress
waiting_client
approved
reserved
in_preparation
on_site
completed
cancelled
archived
```

Проектный статус не подменяет отдельные статусы резерва, нехватки, субаренды и складской операции.

Статусы проекта должны быть расширяемыми через настройки только в пределах допустимой модели переходов.

## 9. Sections

Разделы — это содержательная часть сметы.

Примеры разделов:

- Stage;
- Truss;
- LED;
- Sound;
- Light;
- Backline;
- Commutation;
- Services;
- Crew;
- Transport;
- Custom.

Раздел может быть:

- ручным;
- собранным из справочника;
- рассчитанным формулой;
- созданным из 3D-сцены;
- импортированным.

Пометка о планируемой субаренде в интерфейсе раздела не создаёт запись `subrent` напрямую. Реальная субаренда оформляется через контекст `subrent` после появления подтверждённой потребности или нехватки.

## 10. Optional Scene

3D-сцена является опциональной частью проекта.

```text
optionalScene: null | SceneModelReference
```

Если 3D не нужен, ссылка может отсутствовать.

Если 3D используется, сцена должна быть связана с проектными разделами и BOM через публичные контракты `three-d-scene`, `sections` и `bom`.

ProjectQuote не должен встраивать внутреннюю модель 3D-модуля как собственное изменяемое состояние.

## 11. BOM Demand

BOM — техническая потребность проекта.

BOM может формироваться из:

- ручных строк сметы;
- технических разделов;
- 3D-сцены;
- шаблонов;
- складских комплектов;
- импортированных данных.

Базовая строка потребности должна содержать минимум:

- id;
- projectQuoteId;
- sectionId;
- sourceType;
- sourceReferenceId;
- catalogItemId;
- inventoryItemId при наличии связи;
- name;
- code;
- requiredQuantity;
- unit;
- weight;
- power;
- price;
- notes.

Следующие значения не принадлежат строке BOM как источнику истины:

```text
availableQuantity
reservedQuantity
shortageQuantity
subrentQuantity
```

Они могут возвращаться рядом со строкой как рассчитанная fulfillment projection, построенная из данных владельцев соответствующих контекстов.

`bom` нормализует потребность и происхождение строки. Он не резервирует оборудование, не закрывает нехватку и не создаёт складское движение.

## 12. Fulfillment Projection

Проекту нужна сводная read model обеспечения, например:

- `not_checked`;
- `available`;
- `partially_available`;
- `reserved`;
- `shortage_open`;
- `subrent_in_progress`;
- `ready_for_issue`;
- `issued`;
- `returned`;
- `closed`.

Проекция может содержать:

- сводный статус;
- рассчитанные количества;
- `reservationIds`;
- `shortageIds`;
- `subrentIds`;
- ссылки на активные складские операции;
- `calculatedAt`;
- версию read model.

Проекция:

- не изменяется прямым CRUD из ProjectQuote;
- может быть пересобрана из источников истины;
- не используется для обхода проверок `reservations`, `shortages` или `warehouse-operations`;
- может быть временно устаревшей, поэтому критическое действие всегда повторно проверяется владельцем данных.

Коммерческая смета может быть подготовлена до складской проверки. Отсутствие fulfillment projection не должно ломать ProjectQuote.

## 13. Crew

Команда проекта:

- роль;
- пользователь;
- приглашённый специалист;
- ставка;
- часы;
- смены;
- комментарии;
- доступ к проекту.

В клиентских документах может показываться только роль, без имени конкретного исполнителя.

Во внутренних документах может показываться роль и имя.

## 14. Transport

Транспорт:

- тип транспорта;
- количество машин;
- маршрут;
- стоимость;
- водитель;
- комментарий;
- ссылки на связанные складские выдачи.

ProjectQuote не меняет состояние складской выдачи напрямую.

## 15. Documents

Документы проекта:

- коммерческое предложение;
- техническая сводка;
- складской лист;
- монтажный лист;
- внутренний расчёт;
- схема сцены;
- акт / закрывающие документы в будущем.

Документы должны генерироваться из ProjectQuote и подтверждённых read models других контекстов, а не из случайного состояния интерфейса.

Документ, содержащий складские данные, должен фиксировать версию или время полученного снимка.

## 16. Totals

Итоги:

- сумма аренды;
- сумма услуг;
- сумма транспорта;
- сумма команды;
- плановая и подтверждённая сумма субаренды;
- скидка;
- маржа;
- налоговые поля в будущем;
- общий итог для клиента;
- внутренний итог.

Подтверждённая стоимость субаренды поступает из `subrent`. ProjectQuote может использовать её в итогах, но не владеет процессом подтверждения субаренды.

## 17. Permissions

Права внутри проекта:

- кто может смотреть проект;
- кто может редактировать коммерческую часть;
- кто может редактировать техническую часть;
- кто может запрашивать складскую проверку;
- кто может утверждать проект;
- кто может экспортировать документы;
- кто может видеть внутреннюю себестоимость.

Права на резервы, дефициты, субаренду и складские операции проверяются соответствующими контекстами:

```text
reservations.*
shortages.*
subrent.*
warehouse_operations.*
```

Проектный permission не должен автоматически предоставлять складской permission.

## 18. History

Проектная история фиксирует важные действия ProjectQuote:

- создание;
- изменение статуса;
- изменение клиента;
- изменение суммы;
- изменение технических разделов;
- запрос складской проверки;
- привязку или изменение сводного fulfillment status;
- изменение PDF-настроек;
- назначение команды;
- экспорт документов;
- закрытие проекта.

Отдельные доменные истории принадлежат владельцам данных:

- история резерва — `reservations`;
- история нехватки и предложений результата — `shortages`;
- история субаренды — `subrent`;
- выдача, возврат, перемещение и списание — `warehouse-operations`.

ProjectQuote может показывать объединённую временную линию через read model, но не становится владельцем чужих событий.

Системный `audit` хранится отдельно и не заменяет проектную или доменную историю.

## 19. Межмодульное взаимодействие

ProjectQuote обращается к другим контекстам только через публичные application contracts или ports.

Допустимо:

```text
requestProjectReservation(...)
getProjectFulfillmentProjection(...)
getProjectShortageSummary(...)
```

Запрещено:

```text
ProjectQuote
→ direct inventory table mutation
→ direct shortage status update
→ direct warehouse issue creation
```

## 20. Главный принцип модели

ProjectQuote не должен быть просто набором полей интерфейса и не должен поглощать состояния соседних контекстов.

Это доменная модель, из которой должны строиться:

- экран проекта;
- смета;
- потребность BOM;
- запросы на складское обеспечение;
- ссылки и проекции обеспечения;
- PDF;
- проектная история;
- отчёты;
- статусы;
- интеграции.

Складские остатки, резервы, дефициты, субаренда и движения остаются источниками истины в своих модулях.
