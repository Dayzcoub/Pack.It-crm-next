# 04. План документации PACK.IT

## 1. Цель

Перед началом активной разработки нужно подготовить такую документацию, чтобы приложение не росло хаотично.

Документация должна ответить на вопросы:

- что является ядром продукта;
- какие модули и продуктовые контексты входят в систему;
- какие роли, permissions и scopes существуют;
- как устроен проект;
- как разделены склад, резервы, дефициты, субаренда и операции;
- когда нужен 3D-конструктор;
- как формируются документы;
- как защищаются данные;
- как приложение будет развиваться по этапам.

## 2. Уже созданные базовые документы

- `00_PRODUCT_PRINCIPLES.md` — продуктовые принципы.
- `01_SYSTEM_ARCHITECTURE.md` — верхнеуровневая архитектура и карта продуктовых контекстов.
- `02_PROJECT_QUOTE_DOMAIN.md` — модель проекта/сметы и граница складских read models.
- `03_ADMIN_ROLES_ACCESS.md` — системная админка, роли, permissions и scopes.
- `05_INVENTORY_RESERVATIONS.md` — канонические границы `catalog`, `inventory`, `reservations`, `shortages`, `subrent`, `warehouse-operations`, lifecycle нехватки и предложения результата.
- `09_BACKEND_DATA_ARCHITECTURE.md` — техническая база модульного монолита, shared contracts, backend/data, frontend-границы, realtime, workers, CI и architecture checks.

Документ `09_BACKEND_DATA_ARCHITECTURE.md` фиксирует техническое направление, но оставляет открытыми конкретные ADR по runtime/framework, ORM, auth, PostgreSQL version/ID strategy, multi-tenancy, RLS и production provider.

Документ `05_INVENTORY_RESERVATIONS.md` является каноническим для складского контура. Атомарные файлы `25_WAREHOUSE_10_xxx.md` должны соответствовать его владельцам данных и permission-модели.

## 4. Правило именования документов

Документы нумеруются по смысловому порядку:

```text
00_...
01_...
02_...
```

Номер не означает версию. Версии продукта должны идти отдельно.

ADR хранятся в `docs/adr/` и имеют собственную последовательную нумерацию.

## 5. Правило изменения документов

Если решение меняется, документ нужно обновлять, а не оставлять старый текст как равноправный вариант.

Если нужно сохранить спорный вариант, его можно вынести в раздел:

```text
Open Questions
```

или

```text
Rejected Alternatives
```

Атомарные decision notes не должны переопределять владельцев данных или permission-модель канонических доменных документов.

## 6. Ближайший приоритет

```text
1. Завершить архитектурную сверку существующих warehouse decision notes с 05_INVENTORY_RESERVATIONS.md
2. Уточнить optional 3D и документы/PDF
3. Зафиксировать UI/UX и границу web/website
4. Принять ADR по runtime, DB/ORM, auth и multi-tenancy
5. Подготовить development phases и bootstrap plan
6. Реализовать architecture:check до появления большого объёма кода
```

Складской доменный baseline считается созданным, когда:

- владельцы данных не пересекаются;
- ProjectQuote хранит только потребность, ссылки и read models;
- permissions разделены по контекстам;
- предложения результата принадлежат `shortages`;
- уведомления и audit не подменяют бизнес-решение;
- конфликтующие ранние decision notes перепривязаны.
